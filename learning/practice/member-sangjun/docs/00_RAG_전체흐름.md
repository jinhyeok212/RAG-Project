# RAG 전체 흐름

이 프로젝트는 완성형 챗봇을 만드는 것이 아니라, RAG가 어떤 단계로 작동하는지 이해하기 위한 실험입니다.

## 우리가 만드는 RAG

처음 구현하는 것은 Retrieval-only RAG입니다.

Retrieval-only RAG는 LLM이 답변을 생성하기 전 단계까지만 구현합니다.

```text
질문
-> 질문과 비슷한 문서 조각 검색
-> 검색 결과 출력
-> 검색 결과 안에 정답이 있는지 평가
```

즉, 아직 "자연스러운 문장으로 답변 생성"은 하지 않습니다.

## 전체 파이프라인

```text
AIHub 기계독해 데이터
        |
        v
context / question / answer 분리
        |
        v
context를 청크로 나누기
        |
        v
청크를 임베딩 벡터로 변환
        |
        v
FAISS 벡터DB에 저장
        |
        v
question을 임베딩 벡터로 변환
        |
        v
가장 비슷한 청크 Top-k 검색
        |
        v
검색된 청크 안에 answer가 있는지 평가
```

## AIHub 데이터의 역할

AIHub 기계독해 데이터는 보통 다음 구조를 가집니다.

```text
context  = 본문
question = 본문을 보고 만든 질문
answer   = 본문 안에 있는 정답
```

이 프로젝트에서는 세 항목을 이렇게 씁니다.

| 항목 | 사용 위치 | 의미 |
| --- | --- | --- |
| context | 벡터DB에 저장 | 검색 대상 문서 |
| question | 평가 입력 | 사용자가 던지는 질문 역할 |
| answer | 평가 기준 | 검색이 맞았는지 확인하는 정답 |

## 중요한 구분

벡터DB에 들어가는 것은 `context`입니다.

`question`은 검색할 때 입력으로 사용합니다.

`answer`는 검색 결과를 채점할 때만 사용합니다.

```text
벡터DB: context 청크
입력: question
채점 기준: answer
```

## 왜 LLM을 나중에 붙이나?

RAG가 틀렸을 때 원인은 크게 두 가지입니다.

```text
1. 검색이 틀림
2. 검색은 맞았지만 LLM이 답변을 잘못 생성함
```

처음부터 LLM을 붙이면 문제가 어디에서 생겼는지 구분하기 어렵습니다.

그래서 먼저 검색만 구현합니다.

검색 결과에 정답이 들어오면 검색 단계는 어느 정도 성공한 것입니다.

검색 결과에 정답이 없으면 청킹, 임베딩, Top-k 설정, 데이터 전처리를 먼저 의심해야 합니다.
