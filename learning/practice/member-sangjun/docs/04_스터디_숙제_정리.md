# 스터디 숙제 정리

이번 주 학습의 핵심은 API를 호출해 답변을 받는 것이 아니라, RAG의 각 단계와 실패 원인을 팀이 직접 확인하는 것입니다.

## 이번 프로젝트의 목적

이 프로젝트는 완성형 챗봇을 만드는 것이 아닙니다.

목적은 RAG가 다음 순서로 작동한다는 것을 직접 확인하는 것입니다.

```text
문서 준비
-> 청킹
-> 임베딩
-> 벡터DB 저장
-> 질문 임베딩
-> Top-k 검색
-> 검색 결과 평가
```

현재 UI는 이 과정을 보기 쉽게 만든 학습 도구입니다.

## 현재 구현한 범위

| 단계 | 구현 여부 | 설명 |
| --- | --- | --- |
| AIHub 데이터 사용 | O | 기계독해 데이터의 context/question/answer 사용 |
| context 추출 | O | 검색 대상 문서로 사용 |
| question 추출 | O | 검색 테스트 입력으로 사용 |
| answer 추출 | O | 검색 결과 평가 기준으로 사용 |
| 청킹 | O | 300자, 700자 비교 |
| 임베딩 | O | `intfloat/multilingual-e5-small` 사용 |
| 벡터DB | O | FAISS 사용 |
| Top-k 검색 | O | Top-k 3, 5 비교 |
| 검색 평가 | O | 검색 결과 안에 answer가 포함되는지 확인 |
| 채팅형 UI | O | 질문 입력, 핵심 답변, 근거 확인 |
| LLM 답변 생성 | X | 아직 연결하지 않음 |

## 중요하게 봐야 하는 포인트

### 1. context만 벡터DB에 넣는다

AIHub 데이터에는 `context`, `question`, `answer`가 있습니다.

이번 실험에서는 `context`만 벡터DB에 넣습니다.

```text
context = 검색할 문서
question = 사용자가 넣는 질문 역할
answer = 검색이 맞았는지 확인하는 정답
```

`answer`까지 벡터DB에 넣으면 검색이 너무 쉬워져서 RAG 검색 과정을 제대로 평가하기 어렵습니다.

### 2. 청킹은 검색 단위를 만드는 과정이다

긴 context를 통째로 검색하면 질문과 상관없는 내용까지 같이 들어올 수 있습니다.

그래서 문서를 작은 조각으로 나눕니다.

```text
긴 context
-> chunk 1
-> chunk 2
-> chunk 3
```

청크가 너무 작으면 정답 문장이 끊길 수 있습니다.

청크가 너무 크면 불필요한 내용이 같이 검색될 수 있습니다.

### 3. 임베딩은 문장을 숫자 벡터로 바꾸는 과정이다

문장 그대로는 FAISS가 비교할 수 없습니다.

그래서 임베딩 모델로 문장을 숫자 배열로 바꿉니다.

```text
"이번 포럼의 주제는 청소년과 뉴미디어다."
-> [0.12, -0.04, 0.77, ...]
```

질문도 벡터로 바꾸고, 문서 청크도 벡터로 바꾼 뒤 서로 가까운 것을 찾습니다.

### 4. FAISS는 비슷한 벡터를 찾아준다

FAISS는 질문에 답을 생성하지 않습니다.

FAISS가 하는 일은 이것입니다.

```text
질문 벡터와 가장 가까운 문서 청크 벡터 Top-k 찾기
```

즉, FAISS는 검색기입니다.

### 5. Retrieval-only는 LLM 없이 검색만 확인하는 단계다

현재 프로젝트는 Retrieval-only RAG입니다.

```text
질문
-> 관련 문서 검색
-> 핵심 근거 표시
```

아직 LLM이 답변을 새로 생성하지 않습니다.

이렇게 하는 이유는 검색이 잘 되는지 먼저 확인하기 위해서입니다.

## 현재 실험 결과

| 청크 크기 | Top-k | 질문 수 | 정답 포함 수 | Recall |
| --- | ---: | ---: | ---: | ---: |
| 300 | 3 | 30 | 28 | 93.33% |
| 300 | 5 | 30 | 29 | 96.67% |
| 700 | 3 | 30 | 30 | 100% |
| 700 | 5 | 30 | 30 | 100% |

여기서 Recall은 다음 뜻입니다.

```text
전체 질문 중 검색된 Top-k 청크 안에 정답이 들어온 비율
```

이번 샘플에서는 700자 청크가 300자 청크보다 정답 포함률이 높았습니다.

하지만 항상 700자가 좋은 것은 아닙니다.

문서 종류가 바뀌면 너무 큰 청크 때문에 불필요한 정보가 많이 섞일 수도 있습니다.

## 실패 원인을 어떻게 확인할까?

RAG가 틀렸을 때는 다음 순서로 확인합니다.

### 1. 검색 결과에 정답이 있는가?

검색된 근거 안에 정답이 없다면 검색 단계 문제입니다.

의심할 수 있는 원인:

- 청크가 너무 작아서 정답이 잘림
- 청크가 너무 커서 관련 없는 내용이 섞임
- Top-k가 너무 작아서 정답 청크가 누락됨
- 질문 표현과 문서 표현이 달라 임베딩 검색이 실패함
- 원본 데이터 전처리가 잘못됨

### 2. 검색 결과에는 정답이 있는데 답변이 틀렸는가?

이 경우는 LLM을 붙였을 때 주로 생기는 문제입니다.

의심할 수 있는 원인:

- 프롬프트가 불명확함
- LLM이 근거 외 내용을 지어냄
- 여러 근거가 충돌함
- 문서에 없는 질문인데 LLM이 억지로 답함

현재 프로젝트는 아직 LLM을 붙이지 않았기 때문에 이 문제를 일부러 분리해서 보고 있습니다.

## 팀원이 설명할 수 있어야 하는 것

스터디가 끝났을 때 팀원이 다음 질문에 답할 수 있으면 성공입니다.

```text
1. 왜 문서를 청크로 나누는가?
2. 임베딩은 무엇을 표현하는가?
3. 벡터DB는 어떤 역할을 하는가?
4. Top-k는 검색 결과에 어떤 영향을 주는가?
5. answer를 왜 벡터DB에 넣지 않는가?
6. 검색 결과가 틀렸을 때 어디를 의심해야 하는가?
7. 검색 결과가 맞아도 LLM 답변이 틀릴 수 있는 이유는 무엇인가?
8. 문서에 답이 없을 때 어떻게 답변을 제한해야 하는가?
```
