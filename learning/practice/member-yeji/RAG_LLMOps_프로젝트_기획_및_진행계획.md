# RAG 운영 품질 진단 및 개선을 위한 LLMOps 플랫폼

## 1. 프로젝트명

**RAG 서비스 운영 로그 기반 품질 진단 및 지속적 개선을 위한 LLMOps 플랫폼**

## 2. 프로젝트 한 줄 소개

RAG 서비스에서 발생하는 질문, 검색 문서, 생성 답변, 품질 평가 점수, 비용, 응답시간 등의 운영 로그를 수집·분석하여 **품질 저하 원인과 개선 방법을 운영자에게 제공하는 LLMOps 관리자 플랫폼**을 구축한다.

## 3. 프로젝트 배경

RAG 기반 챗봇은 회사 문서나 외부 지식 문서를 검색한 뒤 해당 내용을 근거로 답변을 생성한다.

```text
사용자 질문
→ 관련 문서 검색
→ 검색 문서를 참고한 답변 생성
→ 사용자에게 답변 전달
```

하지만 실제 운영에서는 다음과 같은 문제가 발생할 수 있다.

- 질문과 관련 없는 문서를 검색한다.
- 필요한 문서를 검색하지 못한다.
- 검색 문서에 없는 내용을 답변한다.
- 질문과 관계없는 답변을 생성한다.
- 응답시간이나 토큰 비용이 지나치게 증가한다.
- 설정 변경 후 실제 품질이 개선됐는지 판단하기 어렵다.
- 문제가 검색 단계인지 생성 단계인지 구분하기 어렵다.

따라서 RAG 챗봇을 만드는 것뿐만 아니라, **RAG가 제대로 작동하는지 지속적으로 평가하고 문제의 원인을 진단하는 운영 시스템**이 필요하다.

## 4. 문제 정의

RAG 서비스를 실제로 운영하려면 단순히 답변이 생성되는지만 확인해서는 안 된다. 운영자는 다음 질문에 답할 수 있어야 한다.

- 올바른 문서를 검색했는가?
- 답변이 검색 문서를 근거로 작성되었는가?
- 사용자의 질문에 적절하게 답했는가?
- 근거 없는 답변이나 환각이 발생하지 않았는가?
- 품질이 낮아진 원인이 검색인지 답변 생성인지 알 수 있는가?
- 어떤 질문 유형과 문서에서 실패가 많이 발생하는가?
- 품질 대비 비용과 응답시간은 적절한가?
- RAG 설정을 변경한 후 실제로 품질이 개선되었는가?

그러나 여러 평가 지표가 각각 다른 점수로 제공되기 때문에, 운영자가 이를 종합하여 **현재 답변을 신뢰해도 되는지, 무엇을 개선해야 하는지 판단하기 어렵다.**

이에 본 프로젝트에서는 RAG 실행 로그와 평가 지표를 통합하여 답변의 품질 상태, 위험 수준, 실패 원인 및 개선 방법을 제공하는 LLMOps 플랫폼을 개발한다.

## 5. 프로젝트 핵심 목표

```text
RAG 실행
→ 운영 로그 수집
→ 품질·비용·응답시간 평가
→ 실패 원인 진단
→ 설정별 성능 비교
→ 운영자에게 개선 방법 제공
```

### 세부 목표

- RAG 전체 실행 과정 추적
- 검색 품질과 답변 품질 분리 평가
- 품질·비용·응답시간 통합 분석
- 질문 유형과 문서 유형별 실패 분석
- 설정 변경 전후 성능 비교
- 규칙 기반 Decision Engine 구축
- 관리자용 대시보드 제공
- 필요하면 예측 모델로 확장

# 6. 다음 주까지의 사전 학습 단계

## 6.1 사전 학습 목적

현재 팀원들이 RAG와 LLMOps를 처음 학습하는 단계이므로, 바로 역할을 나누어 본 프로젝트를 개발하면 일부 팀원만 전체 흐름을 이해할 가능성이 있다.

따라서 다음 주까지 6명 전원이 각자 간단한 RAG를 구현하며 다음 흐름을 직접 경험한다.

```text
문서 준비
→ 문서 분할
→ 임베딩
→ Vector DB 저장
→ 질문 입력
→ 관련 문서 검색
→ LLM 답변 생성
→ 결과 확인
```

이 단계의 목표는 완성도 높은 서비스를 만드는 것이 아니라, **모든 팀원이 RAG의 입력·출력과 전체 동작 흐름을 이해하는 것**이다.

## 6.2 개인 RAG 구현 범위

### 필수 구현

- 문서 5~20개 준비
- 문서를 Chunk 단위로 분할
- 임베딩 모델 적용
- FAISS 또는 Chroma에 저장
- 사용자 질문 입력
- 유사 문서 Top-k 검색
- 검색 문서를 바탕으로 LLM 답변 생성
- 검색된 문서와 답변을 함께 출력

### 필수 확인 항목

- Chunk란 무엇인가?
- Embedding은 왜 필요한가?
- Vector DB는 어떤 역할을 하는가?
- Similarity Score는 무엇을 의미하는가?
- Top-k를 변경하면 결과가 어떻게 달라지는가?
- Retriever와 Generator는 각각 무엇을 담당하는가?
- 검색이 실패하면 답변에는 어떤 문제가 생기는가?
- 검색은 성공했지만 LLM이 잘못 답할 수도 있는가?

### 선택 실험

- Chunk size 300 / 500 / 800 비교
- Top-k 3 / 5 / 10 비교
- 서로 다른 임베딩 모델 비교
- 일반 LLM 답변과 RAG 답변 비교
- 검색 문서가 없을 때 답변 거절 프롬프트 적용

## 6.3 개인 구현 권장 기술

```text
언어: Python
RAG 프레임워크: LangChain 또는 직접 구현
Vector DB: FAISS 또는 Chroma
데이터: KorQuAD 1.0 일부 또는 개인 문서
LLM: 팀이 공통으로 사용할 수 있는 API/오픈소스 모델
UI: 콘솔 또는 Streamlit
```

처음부터 복잡한 Agent, Fine-tuning, Kubernetes 등을 사용하지 않는다.

## 6.4 다음 주 개인 결과물

- 실행 가능한 개인 RAG 코드
- RAG 전체 흐름을 설명하는 간단한 문서
- 정상 답변 사례 2개
- 검색 실패 사례 1개
- 생성 실패 사례 1개
- 사용한 Chunk size와 Top-k
- 구현하면서 이해되지 않은 점
- 본 프로젝트에 적용하고 싶은 기능 1개

### 발표 방법

한 명당 약 10분으로 진행한다.

```text
5분: 구현한 RAG 시연
3분: 실패 사례 설명
2분: 배운 점과 질문 공유
```

## 6.5 다음 주 팀 회의에서 결정할 사항

1. 개인 RAG 시연 및 실패 사례 비교
2. 공통 용어와 RAG 전체 흐름 확인
3. 프로젝트 문제 정의와 MVP 확정
4. 공통 기술 스택 결정
5. 메인 데이터셋과 샘플 규모 확정
6. 공통 Baseline RAG 구조 결정
7. 6인 역할 분담
8. 첫 번째 스프린트 업무 배정

개인 RAG 중 하나를 그대로 선택하기보다 장점을 조합해 팀의 공통 Baseline RAG를 만든다.

```text
개인 RAG 6개 비교
→ 구현 방식과 결과 공유
→ 공통 구조 결정
→ 팀 저장소에 Baseline RAG 구축
```

# 7. 데이터셋 계획

## 7.1 데이터 사용 원칙

메인 주제는 특정 고객지원 챗봇이 아니라 **여러 RAG 서비스를 관리할 수 있는 운영 플랫폼**으로 유지한다. 고객지원 데이터는 이를 보여주는 적용 사례로 선택적으로 활용한다.

| 단계 | 데이터셋 | 활용 목적 |
|---|---|---|
| 개인 학습·초기 개발 | KorQuAD 1.0 | 구조가 단순해 RAG 파이프라인 구현에 적합 |
| 메인 실험 | KorQuAD 2.1 | 긴 문서 기반 검색 및 설정별 성능 평가 |
| 품질 고도화 | AI Hub 기계독해 데이터 | 정답 없는 질문, 답변 거절, 근거 불충분 평가 |
| 선택 적용 사례 | AI Hub 민원 콜센터·소상공인 QA | FAQ 문서로 재구성해 고객지원 시나리오 구현 |
| 영어 보조 실험 | RAGBench·MultiHop-RAG | RAG 평가 구조 및 Multi-hop 실험 참고 |

## 7.2 권장 진행 순서

```text
1단계: KorQuAD 1.0 질문 50~100개로 파이프라인 점검
2단계: KorQuAD 2.1 질문 300~500개로 본 실험
3단계: AI Hub 정답 없는 질문을 추가해 답변 거절 평가
4단계: 여유가 있으면 고객지원 FAQ 시나리오 추가
```

## 7.3 데이터 변환 구조

| 원본 정보 | 프로젝트 컬럼 | 활용 |
|---|---|---|
| 문서 제목 | doc_title | 문서 표시 및 유형 분석 |
| 문서 본문 | text | RAG 검색 대상 |
| 질문 | question | RAG 입력 및 평가 질문 |
| 정답 | ground_truth_answer | 답변 정확성 평가 |
| 문서 ID | ground_truth_doc_id | Hit@k·MRR 계산 |
| 정답 위치·근거 | evidence_text | 근거 회수 및 답변 평가 |
| 정답 없음 여부 | should_answer | 답변 거절 정확도 평가 |

## 7.4 운영 로그 생성 방식

공개 데이터 자체에는 토큰, 비용, 응답시간 등의 운영 로그가 없으므로 팀이 RAG를 여러 설정으로 실행해 로그를 생성한다.

예를 들어 질문 300개를 6개 설정으로 실행하면 약 1,800개의 실험 로그를 확보할 수 있다.

이 데이터는 실제 기업의 운영 로그가 아니라 **RAG 설정별 실험을 통해 직접 생성한 실험 기반 운영 로그**라고 표현한다.

# 9. 품질 평가 기준

## 9.1 검색 평가

| 지표 | 확인 내용 |
|---|---|
| Hit@k | Top-k 안에 정답 문서가 있는가? |
| MRR | 정답 문서가 얼마나 높은 순위에 있는가? |
| Context Precision | 관련 없는 문서를 많이 가져오지 않았는가? |
| Context Recall | 필요한 근거를 빠뜨리지 않았는가? |
| Similarity Score | 질문과 검색 문서가 의미적으로 얼마나 가까운가? |

## 9.2 답변 평가

| 지표 | 확인 내용 |
|---|---|
| Faithfulness | 답변이 검색 문서를 근거로 작성됐는가? |
| Answer Relevancy | 질문에 맞는 답변을 했는가? |
| Answer Correctness | 기준 정답과 비교해 사실이 맞는가? |
| Semantic Similarity | 표현은 달라도 기준 정답과 의미가 비슷한가? |
| Refusal Accuracy | 근거가 없을 때 적절히 답변을 거절했는가? |

## 9.3 운영 평가

| 지표 | 확인 내용 |
|---|---|
| Average Latency | 평균 응답시간 |
| p95 Latency | 느린 요청의 응답시간 |
| Token Usage | 요청별 토큰 사용량 |
| Estimated Cost | 모델 사용 비용 |
| Error Rate | 시스템 오류 비율 |
| Bad Feedback Rate | 부정 사용자 피드백 비율 |

# 10. Decision Engine

여러 평가 지표를 조합하여 운영자가 이해할 수 있는 판단 결과를 만드는 규칙 기반 엔진을 구현한다.

```text
품질 지표 + 비용 + 응답시간
→ Decision Engine
→ Quality Score
→ Risk Level
→ Failure Type
→ 판단 근거
→ 추천 조치
```

## 10.1 출력 예시

```json
{
  "quality_score": 58,
  "risk_level": "HIGH",
  "failure_type": "RETRIEVAL_FAILURE",
  "reason": "정답 문서가 Top-5 검색 결과에 포함되지 않았습니다.",
  "recommended_action": "Hybrid Search 또는 Reranker 적용을 검토하세요."
}
```

## 10.2 초기 판단 규칙 예시

| 조건 | 실패 유형 | 추천 조치 |
|---|---|---|
| Hit@k가 낮음 | Retrieval Failure | Retriever·Embedding 점검 |
| Hit@k는 높지만 MRR이 낮음 | Ranking Failure | Reranker 적용 |
| Context Recall이 낮음 | Evidence Missing | Top-k 또는 Chunk 조정 |
| 검색 성공·Faithfulness 낮음 | Unsupported Answer Risk | 프롬프트·생성 모델 점검 |
| Answer Relevancy가 낮음 | Relevancy Failure | 질문 분류·프롬프트 점검 |
| Latency가 높음 | Performance Issue | 모델·검색 구조 최적화 |
| 비용이 높고 품질 차이가 작음 | Cost Inefficiency | 저비용 모델 검토 |

Faithfulness가 특정 값보다 낮다고 무조건 환각으로 확정하지 않는다. 초기에는 **근거 불충분 위험 또는 Unsupported Answer Risk**로 표현하고, 이후 사람이 검수한 결과로 임계값을 조정한다.

# 13. PyTorch 예측 모델 적용 여부

## 결론

PyTorch 예측 모델은 **MVP 필수가 아닌 조건부 확장 기능**으로 둔다.

초기부터 예측 모델을 만들면 충분한 정답 라벨 없이 Decision Engine의 규칙 결과를 다시 예측하는 모델이 될 수 있다. 따라서 다음 순서로 진행한다.

```text
규칙 기반 Decision Engine 구축
→ 사람이 실패 사례 검수
→ 신뢰할 수 있는 라벨 축적
→ 간단한 Baseline 모델 실험
→ 데이터가 충분하면 PyTorch 모델 개발
```

## 모델 개발 조건

- 검수된 데이터 약 1,000건 이상 확보
- 성공·실패 라벨 기준 확정
- 실패 유형별 데이터 확보
- 학습·검증·테스트 데이터 분리 가능
- MVP 주요 기능 완성

## 예측 목표 예시

- 사용자 불만 발생 가능성
- 답변 실패 확률
- 근거 불충분 위험
- 예상 Failure Type

사전 예측 모델을 만든다면 Ragas 결과처럼 답변 생성 후에만 알 수 있는 값은 입력에서 제외하고 질문 특성, 검색 점수, 검색 설정 등의 값만 사용한다.
