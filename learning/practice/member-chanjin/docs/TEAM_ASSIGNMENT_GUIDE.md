# 팀원 과제 가이드: RAG Core Chatbot 실습

## 과제 목적

본격적인 RAG Quality Monitor 프로젝트에 들어가기 전에, 각 팀원이 RAG의 기본 동작 원리를 직접 경험하는 것이 목적이다. 이 실습 챗봇은 작은 한국어 지식베이스를 사용해 문서 검색, 프롬프트 구성, 답변 생성, 로그 저장 과정을 보여준다.

## 팀원이 해야 할 일

1. 프로젝트를 실행한다.
2. 예시 질문을 최소 3개 입력한다.
3. top_k, chunk_size, similarity_threshold를 각각 한 번 이상 바꿔본다.
4. 검색된 문서와 답변이 어떻게 달라지는지 확인한다.
5. data/logs 폴더의 rag_run_logs.csv와 retrieval_logs.csv를 확인한다.
6. 본인이 이해한 RAG 파이프라인을 5문장으로 정리한다.

## 추천 실습 순서

### 1단계: 기본 질문 실행

다음 질문을 그대로 입력한다.

- RAG가 뭐야?
- RAG에는 어떤 데이터가 필요해?
- LLMOps 대시보드에서 어떤 지표를 봐야 해?

확인할 것:

- 어떤 문서가 검색되는가?
- score가 높은 문서는 질문과 관련 있는가?
- 답변이 검색 문서에 근거하고 있는가?

### 2단계: top_k 비교

같은 질문으로 top_k를 2, 5, 8로 바꿔본다.

관찰 포인트:

- 검색 문서 수가 늘어나면 답변 근거가 풍부해지는가?
- 관련 없는 문서가 섞이는가?
- 예상 token 수가 증가하는가?

### 3단계: chunk_size 비교

같은 질문으로 chunk_size를 400, 700, 1000으로 바꿔본다.

관찰 포인트:

- chunk가 작을 때 문맥이 부족하지 않은가?
- chunk가 클 때 불필요한 내용이 많이 들어가지 않는가?
- 검색 score가 어떻게 달라지는가?

### 4단계: similarity_threshold 비교

threshold를 0.00, 0.10, 0.30으로 바꿔본다.

관찰 포인트:

- threshold가 높아질수록 검색 결과가 줄어드는가?
- 너무 높이면 관련 문서도 사라지는가?
- 너무 낮으면 관련 없는 문서가 들어오는가?

### 5단계: MMR 비교

retrieval_mode를 Top-k와 MMR로 각각 실행한다.

관찰 포인트:

- Top-k 결과가 비슷한 문서에 몰리는가?
- MMR이 조금 더 다양한 문서를 가져오는가?
- 문서가 적을 때는 MMR 효과가 작을 수 있음을 이해한다.

## 제출하면 좋은 결과물

- 실행 화면 캡처 1장
- 질문 3개와 답변 요약
- top_k 비교 결과
- chunk_size 비교 결과
- 본인이 이해한 RAG 파이프라인 설명
- 본 프로젝트에서 맡고 싶은 역할

## 본 프로젝트와의 연결

이 실습에서 저장되는 로그는 최종 프로젝트의 축소판이다. 최종 프로젝트에서는 단순 실행 로그를 넘어 retrieval hit rate, faithfulness, hallucination rate, token cost, latency, p95 latency까지 관리하는 LLMOps 대시보드를 구축한다.
