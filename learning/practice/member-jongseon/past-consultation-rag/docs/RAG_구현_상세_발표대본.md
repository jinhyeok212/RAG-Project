# 과거 상담 사례 검색 기반 RAG 구현 상세 발표대본

발표 기준: `RAG_구현_상세_보고서.pdf`
권장 발표 시간: 약 7~9분
발표 톤: 구현 과정을 설명하되, 단순 기능 나열보다 "왜 그렇게 했는지"를 중심으로 말하기

---

## 1. 도입

안녕하세요.
제가 구현한 프로젝트는 **과거 상담 사례 검색 기반 RAG 시스템**입니다.

이 프로젝트의 목적은 사용자가 고객 문의를 입력했을 때, LLM이 아무 근거 없이 답변을 만들어내는 것이 아니라, 기존 상담 데이터에서 유사한 질문과 상담사 답변을 먼저 검색하고, 그 검색 결과를 근거로 답변을 구성하는 것입니다.

즉, 단순 챗봇이라기보다는 **과거 상담 이력을 검색해서 답변 근거로 활용하는 RAG MVP**라고 볼 수 있습니다.

이번 구현에서는 전체 데이터 중 우선 `카페` 카테고리를 MVP 범위로 잡았고, Train 데이터에서 20,000개의 QA 문서를 만들고, Validation 데이터에서 2,000개의 평가 질문을 만들어 검색 성능까지 측정했습니다.

---

## 2. 전체 구현 범위

먼저 전체 구현 범위를 설명드리겠습니다.

이번 프로젝트에서 구현한 핵심 흐름은 크게 여덟 단계입니다.

첫째, 원천 CSV 데이터의 구조를 분석했습니다.
둘째, 상담 대화 로그에서 질문과 답변을 다시 연결해서 QA 문서 형태로 재구성했습니다.
셋째, 이메일, 전화번호, 주문번호처럼 개인정보로 추정될 수 있는 패턴을 마스킹했습니다.
넷째, 검색에 사용할 `retrieval_text`를 만들고 Train corpus를 생성했습니다.
다섯째, BM25, Dense Exact, Dense ANN, Hybrid RRF 방식의 검색기를 구현했습니다.
여섯째, 간단한 reranker fallback을 적용했습니다.
일곱째, Validation 데이터로 Hit@5, Recall@5, MRR, nDCG, latency를 평가했습니다.
마지막으로 FastAPI와 Streamlit을 이용해서 검색 API와 UI 뼈대를 만들었습니다.

다만 아직 고도화 전 단계인 부분도 있습니다.
현재 Dense 검색은 실제 BAAI 임베딩 모델이 아니라 TF-IDF 기반 fallback으로 구현되어 있고, reranker도 Cross-Encoder가 아니라 lexical overlap 기반 fallback입니다.
그래서 이번 단계는 완성형 상용 RAG라기보다는, **데이터 처리부터 검색 평가까지 이어지는 MVP 구조를 먼저 검증한 단계**라고 설명할 수 있습니다.

## 3. RAG 파이프라인 구조

RAG 파이프라인은 다음 순서로 동작합니다.

먼저 원천 CSV 파일을 읽습니다.
그 다음 `상담번호`와 `상담내순번`을 기준으로 하나의 상담 세션 안에서 발화를 시간 순서대로 정렬합니다.

이후 `QA번호`와 `QA여부`를 기준으로 고객 질문과 상담사 답변을 연결합니다.
질문만 보면 의미가 부족한 경우가 있기 때문에, 이전 1~3개의 발화도 함께 저장했습니다.

그 다음 개인정보 마스킹을 적용하고, 검색 인덱스에 넣을 `retrieval_text`를 만듭니다.
이 텍스트를 기준으로 BM25, Dense, ANN 인덱스를 생성합니다.

사용자가 질문을 입력하면, 검색기는 과거 상담 QA 중 유사한 사례를 찾습니다.
그리고 답변 생성 단계에서는 새 답변을 마음대로 생성하는 것이 아니라, 검색된 과거 상담 답변을 근거로 응답합니다.

이 구조를 선택한 이유는 명확합니다.
RAG에서 가장 중요한 것은 LLM이 답변을 잘 쓰는 것 이전에, **정확한 근거 문서를 잘 찾는 것**이기 때문입니다.
그래서 이번 MVP에서는 생성 모델보다 검색 품질과 평가 체계에 더 집중했습니다.

---

## 4. 데이터 구조 분석

데이터는 `소상공인 고객 주문 질의-응답 텍스트` 데이터셋을 사용했습니다.

원천 데이터는 Training과 Validation 폴더에 CSV 형태로 들어 있었고, 핵심 컬럼은 다음과 같았습니다.

`발화자`는 고객인지 상담사인지 구분하는 컬럼이고, `발화문`은 실제 대화 텍스트입니다.
`카테고리`는 업종 또는 도메인이고, 이번 MVP에서는 이 중 `카페` 카테고리를 사용했습니다.
`QA번호`와 `QA여부`는 질문과 답변을 연결하는 데 사용했습니다.
그리고 `상담번호`와 `상담내순번`은 하나의 상담 안에서 대화 순서를 복원하는 데 사용했습니다.

여기서 중요한 점은, 원천 CSV의 한 행이 바로 검색 문서가 아니라는 점입니다.
RAG에서 검색 문서로 쓰려면 고객 질문과 상담사 답변이 하나의 QA 단위로 정리되어 있어야 합니다.
그래서 단순히 CSV를 읽는 것이 아니라, 상담 흐름을 복원하는 전처리 과정이 필요했습니다.

데이터 구조 분석 결과는 `reports/data_profile.md`와 `reports/data_profile.json`으로 저장했습니다.

## 5. QA 문서 재구성

다음은 QA 문서 재구성 과정입니다.

CSV 데이터는 발화 단위로 되어 있기 때문에, 그대로 검색하면 고객 질문만 나오거나 상담사 답변만 따로 나올 수 있습니다.
그래서 먼저 `상담번호`로 상담 세션을 묶고, `상담내순번`으로 발화 순서를 정렬했습니다.

그다음 `QA여부 = q`이거나 `발화자 = c`인 경우를 고객 질문 후보로 보고, `QA여부 = a`이거나 `발화자 = s`인 경우를 상담사 답변 후보로 보았습니다.

그리고 같은 `QA번호` 안에서 앞선 질문과 뒤따르는 답변을 연결했습니다.

이렇게 해서 하나의 검색 문서는 다음 정보를 갖게 됩니다.

질문 원문, 답변 원문, 이전 문맥, 카테고리, 인텐트, 상담번호, QA번호, 검색용 텍스트, 품질 플래그, 메타데이터입니다.

이 과정이 중요한 이유는 RAG에서 검색 대상이 되는 문서 품질이 낮으면, 아무리 좋은 임베딩 모델이나 LLM을 붙여도 답변 품질이 안정적으로 나오기 어렵기 때문입니다.

## 6. 개인정보 마스킹

상담 데이터에는 개인정보가 들어갈 수 있습니다.
그래서 검색 인덱스에 넣기 전에 이메일, 휴대전화 번호, 주민등록번호 형태, 주문번호나 예약번호로 보이는 패턴을 정규식으로 마스킹했습니다.

예를 들어 이메일은 `[EMAIL]`, 전화번호는 `[PHONE]`, 주민등록번호 패턴은 `[RRN]`, 주문번호로 추정되는 값은 `[ORDER_ID]`처럼 바꾸었습니다.

이번 데이터에서는 실제 개인정보가 많지 않을 수 있지만, 상담 데이터 기반 RAG를 만들 때 개인정보 마스킹은 필수적인 전처리라고 판단했습니다.

## 7. Retrieval Text 구성

검색 인덱스에는 단순히 질문만 넣지 않았습니다.

처음에는 질문만 넣는 방식도 생각할 수 있지만, 상담 데이터에서는 질문이 짧거나 맥락이 생략된 경우가 많습니다.
예를 들어 "그거 취소돼요?" 같은 질문은 이전 대화 없이는 무엇을 취소하는지 알기 어렵습니다.

그래서 검색용 텍스트는 `카테고리`, `인텐트`, `이전 문맥`, `질문`을 함께 넣는 C 버전으로 구성했습니다.

이렇게 한 이유는 검색기가 질문의 표면적인 단어뿐만 아니라, 상담의 의도와 문맥까지 함께 참고하도록 하기 위해서입니다.

현재 MVP에서 사용한 버전은 C입니다.

## 8. MVP 데이터 범위

이번 MVP는 전체 데이터를 한 번에 다 처리하기보다는, 우선 하나의 카테고리에서 구조가 제대로 동작하는지 확인하는 방식으로 진행했습니다.

선택한 카테고리는 `카페`입니다.
Train QA 문서는 20,000개, Validation query는 2,000개로 제한했습니다.

이렇게 범위를 제한한 이유는 두 가지입니다.

첫째, 검색기와 평가 파이프라인이 정상적으로 동작하는지 빠르게 검증하기 위해서입니다.
둘째, 전체 데이터를 한 번에 쓰면 인덱스 생성과 평가 시간이 길어져서 MVP 단계에서 반복 실험이 어려워지기 때문입니다.

생성된 주요 산출물은 `train_rag_corpus.parquet`, `validation_rag_corpus.parquet`, `validation_retrieval_queries.jsonl`입니다.

## 9. 검색기 구현

검색기는 여러 방식을 비교할 수 있도록 구현했습니다.

먼저 BM25는 키워드 기반 sparse retrieval입니다.
고객 주문 상담 데이터에는 상품명, 수량, 결제, 포장, 배송 같은 명확한 키워드가 중요하기 때문에 BM25가 강점을 가질 수 있습니다.

그리고 Dense Exact 검색은 현재 실제 임베딩 모델 대신 scikit-learn의 char-wb TF-IDF를 사용했습니다.
이건 나중에 sentence-transformers 기반 임베딩으로 교체하기 전, 전체 검색 구조가 제대로 동작하는지 확인하기 위한 fallback입니다.

Dense ANN은 SVD로 차원을 줄이고 NearestNeighbors로 근사 검색을 수행했습니다.
이 역시 현재는 FAISS나 HNSW를 붙이기 전의 fallback 구조입니다.

마지막으로 Hybrid RRF는 BM25와 Dense의 검색 결과를 결합하는 방식입니다.
BM25 점수와 Dense 점수는 서로 스케일이 다르기 때문에 점수를 직접 더하지 않고, rank를 기반으로 결합하는 Reciprocal Rank Fusion을 사용했습니다.

이렇게 여러 검색 방식을 만든 이유는 RAG 품질 개선에서 단순히 "검색이 된다"가 아니라, **어떤 검색 방식이 어떤 조건에서 더 좋은지 비교할 수 있어야 하기 때문**입니다.

---

## 10. Reranker와 답변 생성

Reranker는 현재 fallback 방식으로 구현했습니다.

원래 목표는 Cross-Encoder reranker를 적용해서, vector search로 가져온 후보 문서들을 다시 정렬하는 것입니다.
하지만 현재 MVP에서는 실행 환경을 고려해서 query token set과 document token set의 overlap을 계산하는 간단한 lexical reranker를 적용했습니다.

답변 생성도 현재는 LLM을 호출하지 않습니다.
검색된 과거 상담 답변 중 상위 결과의 `answer_original`을 기반으로 응답을 구성합니다.

이 방식의 장점은 hallucination을 줄일 수 있다는 점입니다.
LLM이 새 내용을 만들어내지 않고, 실제 과거 상담 사례를 근거로 답변하기 때문입니다.

물론 단점도 있습니다.
답변이 자연스럽게 재작성되지는 않고, 과거 상담 답변을 그대로 사용하는 방식에 가깝습니다.
따라서 다음 단계에서는 OpenAI API나 로컬 LLM을 붙여서, 검색된 근거 안에서만 자연어 답변을 생성하도록 개선할 수 있습니다.

---

## 11. Validation 평가 구성

검색 성능 평가는 Validation 데이터를 이용했습니다.

중요한 점은 Validation 답변 문서를 Train 검색 corpus에 넣지 않았다는 점입니다.
즉, Validation 자체를 검색하는 것이 아니라, Validation 질문과 유사한 과거 Train 상담 사례를 잘 찾는지를 평가했습니다.

평가 대상 query는 Validation 질문이고, positive 문서는 같은 카테고리와 같은 인텐트를 가진 Train 문서로 설정했습니다.

이 방식은 완전한 정답 문서를 찾는 평가라기보다는, **동일 업무 의도의 과거 상담 사례를 잘 찾는지**를 평가하는 방식입니다.

---

## 12. 검색 평가 지표

검색 평가는 Hit@5, Recall@5, MRR, nDCG@10, 평균 latency, p95 latency를 사용했습니다.

Hit@5는 정답으로 볼 수 있는 문서가 상위 5개 안에 하나라도 포함되는지를 봅니다.
MRR은 첫 번째 정답 문서가 얼마나 높은 순위에 있는지를 봅니다.
nDCG는 관련 문서가 상위에 잘 정렬되어 있는지를 평가합니다.

latency도 함께 측정했습니다.
RAG는 정확도만 높아서는 부족하고, 실제 서비스에서는 응답 속도도 중요하기 때문입니다.

---

## 13. 현재 검색 성능

현재 MVP 기준 검색 성능은 다음과 같습니다.

BM25의 Hit@5는 0.4390으로 가장 높았습니다.
Dense Exact는 0.4100, Dense ANN은 0.3810, Hybrid RRF는 0.4340, Hybrid와 Reranker를 함께 쓴 경우는 0.4320이었습니다.

이 결과를 보면 현재 fallback 환경에서는 BM25가 가장 좋은 성능을 보였습니다.

그 이유는 현재 Dense가 실제 의미 임베딩 모델이 아니라 TF-IDF fallback이기 때문입니다.
또한 상담 데이터에는 상품명, 주문, 결제, 취소처럼 키워드가 중요한 질의가 많기 때문에 BM25가 상대적으로 강하게 나온 것으로 해석할 수 있습니다.

ANN은 Exact Dense보다 성능이 낮았는데, SVD로 차원을 줄이는 과정에서 정보가 일부 손실되었기 때문으로 볼 수 있습니다.

Reranker도 현재는 실제 Cross-Encoder가 아니라 lexical overlap 기반이기 때문에 성능 개선이 제한적이었습니다.

따라서 이 결과는 "BM25가 최종적으로 최고다"라는 뜻보다는, **현재 MVP fallback 기준에서는 BM25가 가장 안정적이고, 다음 단계에서 실제 임베딩 모델과 reranker를 붙여 개선 여지가 있다**는 의미입니다.

## 14. API와 UI

구현된 API는 FastAPI 기반입니다.

주요 엔드포인트는 `/health`, `/search`, `/ask`, `/metrics`입니다.

`/health`는 서버와 인덱스 상태를 확인하고, `/search`는 사용자의 질문에 대해 검색 결과를 반환합니다.
`/ask`는 검색 결과를 이용해 답변을 구성하고, `/metrics`는 평가 결과 요약을 반환합니다.

Streamlit UI도 구현했습니다.
사용자는 질문을 입력하고, 검색 방식과 Top-k를 선택할 수 있습니다.
그리고 카테고리나 인텐트 필터를 적용할 수 있으며, 검색된 과거 상담 사례와 점수를 확인할 수 있습니다.

즉, 현재 UI는 완성형 운영 대시보드라기보다는, RAG 검색 결과와 답변 생성 흐름을 확인하기 위한 MVP 화면입니다.

---

## 15. 현재 구현의 한계

현재 구현에는 명확한 한계도 있습니다.

첫째, Dense retrieval이 실제 딥러닝 임베딩이 아니라 TF-IDF fallback입니다.
둘째, ANN도 FAISS나 HNSW가 아니라 scikit-learn 기반 fallback입니다.
셋째, reranker도 Cross-Encoder가 아니라 lexical overlap 방식입니다.
넷째, 답변 생성은 LLM 기반 자연어 생성이 아니라 과거 상담 답변을 그대로 사용하는 구조입니다.
다섯째, RAGAS 기반의 faithfulness나 answer relevance 평가는 아직 적용하지 않았습니다.

하지만 이 한계는 오히려 다음 단계가 명확하다는 뜻이기도 합니다.
현재는 데이터 처리, 검색기, 평가, API, UI까지 이어지는 전체 뼈대를 먼저 만들었고, 이후 각 컴포넌트를 고도화하면 됩니다.

---

## 16. 다음 고도화 방향

다음 단계에서는 먼저 `BAAI/bge-m3` 같은 실제 임베딩 모델을 연결할 예정입니다.

그다음 FAISS나 HNSW 기반 ANN 인덱스로 교체해서 대규모 검색 성능을 개선할 수 있습니다.

또한 `BAAI/bge-reranker-v2-m3` 같은 Cross-Encoder reranker를 적용해서 검색된 후보 문서의 순서를 더 정확하게 재정렬할 수 있습니다.

답변 생성 단계에서는 OpenAI API나 로컬 LLM을 연결하되, 반드시 검색된 상담 사례 안에서만 답변하도록 출처 기반 prompt를 적용할 수 있습니다.

마지막으로 RAGAS 기반 평가를 추가하면, 검색 품질뿐 아니라 답변의 근거성, 관련성, 정확성까지 평가할 수 있습니다.

## 17. 마무리

정리하면, 이번 프로젝트는 과거 상담 QA 문서 2만 개와 Validation query 2천 개를 이용해 상담 사례 검색 기반 RAG MVP를 구현한 것입니다.

핵심은 단순히 챗봇 화면을 만든 것이 아니라, 상담 데이터를 QA 문서로 재구성하고, 여러 검색 방식을 비교하고, 실제 지표로 검색 성능을 평가했다는 점입니다.

현재 결과에서는 BM25가 Hit@5 기준 0.4390으로 가장 좋은 성능을 보였고, Dense와 reranker는 fallback 구조이기 때문에 다음 고도화 단계에서 실제 PyTorch 기반 임베딩 모델과 Cross-Encoder reranker로 개선할 수 있습니다.

따라서 이 프로젝트는 RAG를 단순히 사용하는 데서 끝나는 것이 아니라, **데이터 구축, 검색 실험, 성능 평가, API/UI 구현까지 연결한 RAG 운영형 MVP**라고 정리할 수 있습니다.

감사합니다.
